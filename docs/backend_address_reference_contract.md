# Передача адресов `db.realty` в парсер ЕЖД

Парсер не подключается к PostgreSQL. Backend формирует снимок канонических МКД из
`db.realty` вместе с `db.address` и передаёт его в multipart-поле `address_reference`
при вызове `POST /api/v1/jobs` (тот же параметр поддерживают `/parse` и
`/parse/normalized`).

```json
{
  "version": "2026-09-09T10:00:00Z",
  "buildings": [
    {
      "reference_id": "стабильный идентификатор МКД или ключ снимка",
      "kladr": "01770000000000203",
      "street": "Новочеркасский",
      "house": "9",
      "building": null,
      "structure": null
    }
  ]
}
```

## Требования к выборке backend

- Одна строка на уникальную комбинацию `street + house + building + structure`;
  квартиры в снимок не включать.
- Брать только действующие эталонные объекты недвижимости компании. Не включать
  автоматически созданные импортом дубли с синтетическим лицевым счётом.
- `street` и остальные компоненты передавать в том виде, в котором backend ожидает
  найти существующий объект. `kladr` нужен для аудита совпадения, но сам по себе не
  заменяет проверку дома/корпуса/строения.
- Пустой или противоречивый снимок — ошибка вызова, а не повод запустить парсер без
  справочника.

## Поведение парсера

Нечёткое сравнение применяется только к названию улицы. Дом, корпус и строение
сопоставляются после технической нормализации без числового fuzzy-поиска. При
единственном совпадении парсер возвращает канонические компоненты из снимка, сохраняя
номер квартиры из ЕЖД.

Если совпадения нет или оно неоднозначно, файл завершается с кодом
`PROPERTY_ADDRESS_NOT_IN_REFERENCE`; callback имеет `status=failed`, поэтому
`api.document_import_done` не должен вызываться и новая карточка недвижимости не
создаётся.

До подключения нового параметра parser сохраняет прежнее обратно совместимое
поведение со встроенным справочником обслуживаемых домов.
